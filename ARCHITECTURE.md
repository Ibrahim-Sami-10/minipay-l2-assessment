# MiniPay Architecture

MiniPay is a small three-layer payment service:

```text
Browser UI
    |
    | HTTP/JSON, X-API-Key
    v
Flask/Gunicorn API (:8080)
    |
    | psycopg2, parameterized SQL
    v
PostgreSQL (:5432)
```

The browser dashboard is served as static content by the API. The API exposes
health endpoints, customer operations, payment creation and lookup, payment
history, authentication with `X-API-Key`, and idempotent payment submission
with `Idempotency-Key`.

PostgreSQL stores customers, transactions, callback attempts, and idempotency
keys. The database volume is persistent in Compose and uses a PersistentVolumeClaim
in Kubernetes. Seed data is synthetic and generated by
`database/generate_data.py`.

## Runtime configuration

Non-sensitive database connection settings are supplied through environment
variables or a Kubernetes ConfigMap. `POSTGRES_PASSWORD` and `API_KEY` are
supplied through `.env` locally and a Kubernetes Secret in the cluster. Real
values are intentionally excluded from Git.

## Operational controls

- `/health/live` checks process liveness.
- `/health` checks API-to-database connectivity.
- API requests receive an `X-Request-ID` for support correlation.
- Gunicorn provides multiple API workers in the container.
- Kubernetes deployments define resource requests/limits and probes.
- SQL uses parameters for user-controlled values and dedicated indexes are
  documented in `sql/PERFORMANCE.md`.
